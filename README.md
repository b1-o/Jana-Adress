# Jana Address — разбор адресных строк (Кейс 1, Jana Post × Terricon Valley)

Сервис принимает строку адреса «как её ввёл клиент» и возвращает структурированный ответ:
`province · city · district · living_area · street_type · street_name · house · apartment · entrance · floor · landmark · confidence`.

Работает **автономно**: справочник (КАТО + OpenStreetMap) лежит внутри образа, внешние сервисы на этапе
разбора не вызываются. Интернет нужен только один раз — при подготовке справочника.

---

## 1. Быстрый старт

```bash
docker compose up --build          # интерфейс и API: http://localhost:8000
```

Без Docker:

```bash
pip install -r requirements.txt
# тесты:      python -m pytest tests -q
# пересборка справочника (нужны pandas/shapely): pip install -r requirements-data.txt
```

Проверка после запуска:

```bash

curl -s -X POST localhost:8000/api/parse -H 'Content-Type: application/json' \

python3 scripts/eval.py            # метрика на своём наборе
```

## 2.1 Проверка работоспособности за 2 минуты

**В интерфейсе (http://localhost:8000):**

1. кнопка **«Пример»** → **«Разобрать»** — появится таблица с 8 строками (все сложные кейсы из ТЗ);
2. отметить **«только неуверенные (< 0.6)»** — видно, что фильтр для ручной правки работает;
3. щёлкнуть любую ячейку (например, «Улица») и исправить — она подсветится жёлтым, правка попадёт в выгрузку;
4. **«Скачать JSON»** — формат ответа совпадает с ТЗ (14 полей, `raw_address` без изменений);
5. **«Загрузить файл»** → `data/sample_input.json` (30 строк), затем **«Проверить по эталону»** →
   `data/sample_output.json` — в блоке «Проверка по эталону» появится таблица точности по полям;
6. ссылка **`/docs`** — Swagger, где можно потыкать `/api/parse` и `/api/parse/batch` руками.

**В консоли (из корня проекта):**

```bash
curl -s localhost:8000/api/health                    # статус + размеры справочника
curl -s localhost:8000/api/gazetteer/lookup?q=Аксай   # что справочник знает про «Аксай»
python3 scripts/selfcheck.py                         # справочник + 14 контрольных адресов
python3 scripts/eval.py                              # метрика по нашему эталону (~98.9 %)
python3 tests/test_parser.py                         # 15 тестов на «сложные» строки

# то же самое внутри контейнера (без локального Python):
docker compose exec jana-address python scripts/selfcheck.py
docker compose exec jana-address python scripts/eval.py
docker compose exec jana-address python tests/test_parser.py
```

`scripts/selfcheck.py` печатает отчёт и возвращает код 1, если что-то разошлось — годится и для
быстрой приёмки, и как «доказательство работоспособности» на защите.

## 3. API

| Метод | Назначение |
|---|---|
| `POST /api/parse` | одна строка: `{"raw_address": "...", "id": "rec_1"}` |
| `POST /api/parse/batch` | пакет: `{"addresses":[{"id":"rec_00001","raw_address":"..."}]}` — этим прогонят тестовый набор |
| `POST /api/parse/batch/upload` | файл `.json` / `.csv` / `.txt` (multipart, поле `file`) |
| `GET /api/health` | статус + статистика справочника |
| `GET /api/gazetteer/lookup?q=` | что справочник знает про строку (улица/мкр/город/район) |
| `?debug=1` | добавляет в ответ `_sources` — откуда взято каждое поле («raw», «справочник (по улице)» …) |

Ответ повторяет формат ТЗ один в один (`id`, `raw_address`, …, `confidence`), поэтому его можно
сравнивать с эталоном напрямую.

## 4. Справочник — сердце решения

| Источник | Что даёт | Записей в сборке |
|---|---|---|
| **КАТО НК РК 11-2025** (stat.gov.kz, ред. 18.09.2026) | области, города, районы, сёла/посёлки, RU + KZ | 15 586 |
| **КАТО ред. 18.12.2024** (там же, архив) | **районы в городах**: Алматы 8, Астана 6, Шымкент 5 | 19 |
| **OpenStreetMap** (Overpass: улицы, жилмассивы, микрорайоны) | названия улиц + тип улицы + жилмассивы по городам | **33 095 улиц по 28 городам**, 20 940 жилмассивов |
| **Границы районов Алматы** (`data/districts/`) | полигоны 8 районов — по ним улицы и микрорайоны раскладываются по районам (point-in-polygon) | 8 полигонов |
| **Ручные уточнения** (`data/manual/*.json`) | то, чего нет в открытых данных (напр. «Пришахтинск» → Караганда) | расширяется командой |

> ⚠️ Два подводных камня, найденные при сборе:
> 1. **В действующей редакции КАТО районов в городах нет** — только «г.Алматы», «г.Астана», «г.Шымкент».
>    Список районов берём из предыдущей редакции классификатора (скрипт приложен).
> 2. **Из текущего OSM геометрия районов городов республиканского значения удалена** (отношения
>    остались «пустышками» без участников). Поэтому границы районов Алматы взяты из открытого
>    GeoJSON-экстракта OSM (`data/source/almaty-districts.geo.json`, репозиторий
>    `akilbekov/almaty.geo.json`), а по Астане/Шымкенту в OSM геометрии нет вовсе — там район
>    пока восстанавливается не полностью. Как проверяли: «Мкр Аксай 3а» → «Ауэзовский район»
>    совпадает с официальным примером `sample_output.json` (`rec_00417`).

> 🔎 **Как восстанавливается район.** Улицы и микрорайоны раскладываются по полигонам районов
> (point-in-polygon). Для длинных улиц, которые пересекают несколько районов, берётся «голосование»
> по сегментам: районом считается тот, где лежит большинство сегментов (Розыбакиева → Бостандыкский).
> Пример из ТЗ работает ровно как в эталоне: `город Алматы/Алматы қаласы, Мкр Аксай 3а, 59, кв 70`
> → `district = "Ауэзовский"`.

Пересборка справочника (нужна сеть, ~15 мин на 20 городов):

```bash
make build-all      # КАТО 2026 + районы 2024 → data/gazetteer.sqlite
make fetch-osm      # улицы и жилмассивы по городам (Overpass)
make build-gazetteer
```

Файлы: `data/kato.json`, `data/city_districts.json`, `data/osm/<город>.json`, `data/source/*.xls(x)`
(сырые выгрузки КАТО лежат в репозитории, чтобы справочник можно было пересобрать без интернета).

## 4.1 Три языка: русский, казахский, английский

Адрес разбирается одинаково, на каком бы языке он ни был написан. Отдельный модуль
`app/lang.py` приводит написание к тому виду, в котором хранится справочник.

| Что делаем | Пример |
|---|---|
| Транслитерация латиницы | `Almaty → алматы`, `Abai → абай`, `Shymkent → шымкент`, `Kabanbay batyr → кабанбай батыр` |
| `y` после гласной → «й», иначе → «ы» | `Abay → абай`, `Almaty → алматы` |
| Выбрасываем служебные английские слова **до** транслита | `Almaty city → алматы`, иначе получалось «алматы киты» |
| Типы улиц на трёх языках | `street / st / ave / avenue / boulevard / lane / microdistrict` и `көшесі / даңғылы / шағын ауданы / тас жол` |
| Казахские сокращения | `к-сі`, `көш.`, `даңғ.` |
| Падежи | `Абая → Абай`, `Кенесары → Кенесара` (усечение окончаний как запасной вариант) |

**Правило ТЗ не нарушается:** `street_name` пишется ровно как в строке (`Abai`, а не `Абай`).
Справочник используется только для того, чтобы проверить существование улицы, определить
город, район и тип.

### Примеры

| Адрес | city | street_type | street_name | house |
|---|---|---|---|---|
| `Алматы, улица Абая 12` | Алматы | улица | Абая | 12 |
| `Алматы қаласы, Абай көшесі 12` | Алматы | улица | Абай | 12 |
| `Almaty, Abai street 12` | Алматы | улица | Abai | 12 |
| `Astana city, Kenesary street 40` | Астана | улица | Kenesary | 40 |
| `Shymkent, Tauke khan avenue 5` | Шымкент | проспект | Tauke khan | 5 |
| `Taraz, Tole bi street 55` | Тараз | улица | Tole bi | 55 |

### Проверка языков и точности одной командой

```bash
python scripts/lang_check.py            # кратко, по группам языков
python scripts/lang_check.py --verbose  # разбор каждой строки
python scripts/lang_check.py --only kk  # только казахский
```

Скрипт прогоняет 56 адресов шестью группами — русский, казахский, латиница/английский,
смешанные двуязычные, «грязные» написания и языки, которые система **не** знает, — и
считает по каждой группе: сколько строк разобрано, сколько полей совпало с ожидаемыми
(сравнение как у жюри: нижний регистр, без пунктуации и лишних пробелов), метрику ТЗ
60/25/15 и среднюю уверенность. Работает офлайн.

Свои примеры добавляются в `data/lang_cases.json` (тот же формат, что и встроенные).

### Какие языки поддерживаются, а какие нет

Честно: не «все языки», а три написания казахстанского адреса.

| Язык / написание | Поддержка | Пример |
|---|---|---|
| Русский | ✅ полностью | `Алматы, улица Абая 12, кв 5` |
| Казахский, кириллица | ✅ полностью, включая `қаласы`, `ауданы`, `шағын ауданы`, `пәтер`, `кіреберіс`, `қабат` | `Алматы қаласы, Абай даңғылы 12, 3 пәтер` |
| Английский / латиница | ✅ через транслитерацию в кириллицу | `Almaty, Abay avenue 12, flat 5` |
| Смешанный, двуязычная склейка | ✅ | `город Алматы/Алматы қаласы, Мкр Аксай 3а, 59, кв 70` |
| Турецкий, немецкий, узбекский латиницей | ⚠️ частично: город и дом обычно находятся, тип улицы и служебные слова — нет | `Almaty, Abay Straße 12` → город Алматы, дом 12 |
| Китайский, арабский, японский, корейский | ❌ не поддерживается: строка возвращается с `null` и `confidence ≈ 0`, пакет не падает | `阿拉木图市阿拜街12号` |

Неподдерживаемое письмо не ломает разбор: запись проходит через тот же
`main._parse_one`, поэтому в ответе остаётся `raw_address` дословно и `confidence 0.0`
вместо ошибки 500 на весь пакет.

### Улица не подменяется улицей из другого города

Если город известен из строки, поиск улицы идёт **только в нём**. Раньше при отсутствии
совпадения в городе шёл поиск по всем городам — и «Абай» из Шымкента приносил в ответ
чужой район. Теперь улица из другого города не может испортить `district`.

Если город не указан, справочник, наоборот, помогает его определить — но только по
однозначным совпадениям.

### Жилмассив важнее улицы

«Пришахтинск, ул. Толе батыра 5» — Пришахтинск это жилмассив Караганды, а Толе батыра
есть и в Алматы. Поэтому микрорайон/жилмассив ищется в справочнике **раньше** улицы и
подсказывает город, область и район.

## 4.2 Справочник улиц: что изменилось

Исходная сборка содержала улицы только по пяти городам (Алматы, Астана, Шымкент,
Актобе, Караганда) — 12 344 записи. Для любого другого города улица физически не могла
найтись, поэтому `street_name` брался из строки без проверки, а `confidence` падал.

Скрипт `scripts/expand_streets.py` догружает улицы из OpenStreetMap:

```bash
python scripts/expand_streets.py                 # все города списка
python scripts/expand_streets.py --cities Тараз,Семей
python scripts/expand_streets.py --limit 5
```

Особенности скрипта:

* границы города берутся через Nominatim (bbox), потому что area-запросы Overpass
  находят не все города;
* тип улицы определяется по окончанию названия (`даңғылы → проспект`, `көшесі → улица`);
* на каждое название пишутся две записи: полная (`Алаш даңғылы`) и без типа (`Алаш`);
* прогресс пишется в `data/osm/_streets_progress.json` — можно прервать и продолжить.

Сейчас в сборке **33 095 улиц по 28 городам**: все областные центры плюс крупные
спутники (Талгар, Каскелен, Балхаш, Рудный, Кентау, Темиртау, Экибастуз, Жезказган,
Сатпаев, Конаев).

## 5. Спецификация полей и наши решения

| Поле | Правило | Спорные случаи и наше решение |
|---|---|---|
| `province` | «Актюбинская область», для городов респ. значения — «Алматы» | определяем по городу/району из справочника, если в строке нет |
| `city` | только название, без «город», «пос.», без казахской половины | «Ақтөбе қаласы» → `Актобе` (приводим к русскому написанию по КАТО) |
| `district` | без слова «район» | **написание берём из строки** («Түрксіб»), если поля нет — null (или из справочника, см. ниже) |
| `living_area` | микрорайон/ЖК, когда улица указана отдельно | «мкр Аксай 3а, 59» → `street_type=микрорайон, street_name=Аксай 3а`, `living_area=null` (как в примере ТЗ); «ЖК Томирис, ул. …» → `living_area=Томирис` |
| `street_type` | отдельное слово: улица/проспект/микрорайон/переулок/квартал | если в строке нет — подставляем из OSM (для жюри это «восстановление») |
| `street_name` | без типа, ровно как в строке | падеж и опечатки сохраняем: `казибек би`, `жуалы` |
| `house` | с дробью и литерой: `1/2`, `12а` | `55/6` ≠ `55`; дефис (`33-1`) не превращаем в дробь |
| `apartment/entrance/floor` | только номер | «Курильская 9 кв 1» → дом 9, кв 1; «239кв» → кв 239 |
| `landmark` | ориентир из строки | «магазин береке», «Qazpost Солнечный» |
| `confidence` | 0..1 | растёт с числом распознанных полей, штраф за пустой разбор (≤0.25) |

Дополнительно парсер понимает: невидимые символы внутри строк, `д.`/`дом`/`үй`, `подьезд` (опечатка),
`flat 191`, `kv 12`, `4подьезд`, `11дом`, `69квартира`, казахский порядок («Ақтөбе қаласы»,
«Түрксіб ауданы», «Абай даңғылы»), двуязычные слэши («Алматы/Алматы қаласы»).

## 6. Метрика

`scripts/eval.py` воспроизводит правила оценки из ТЗ:

* адресные поля `province, city, street_name, house` — 60 %;
* детали `apartment, entrance, floor` — 25 %;
* справочные `district, living_area` — 15 %, и только по записям, где они есть в эталоне;
* сравнение посимвольное после нормализации (нижний регистр, без пунктуации);
* если поля нет в эталоне, а решение подняло его из справочника — в метрику не входит (считается
  отдельной колонкой «из справ.», жюри смотрит это на защите).

Текущий результат на нашем наборе (`data/sample_input.json`, 30 строк):

```
address  100.0% × 0.60   details 100% × 0.25   reference 100% × 0.15   → SCORE 100.0%
```

## 8. Ограничения и что делаем дальше

1. **Улица → район.** Границ районов в городах в OSM по Казахстану нет, поэтому привязка
   «улица → район» заполняется частично (сейчас — через жилмассивы и ручные подсказки).
   Варианты: адресный реестр акимата, выгрузка из 2GIS, ручная таблица по частым микрорайонам.
2. **Города OSM.** Улицы собраны по Алматы, Астане, Шымкенту (фоном идёт остальные города —
   `make fetch-osm`, ~15 минут).
3. **Наборы организаторов.** `train.json` / `sample_input.json` / `sample_output.json` от Jana Post
   нам не выдавались — сделан свой набор из 30 размеченных строк. Как получим официальные файлы,
   прогоняем `scripts/eval.py --input train.json --expected sample_output.json` и смотрим ошибки.
4. **Спорные трактовки** (решаем с командой): посёлок в составе города — это `city` («Боралдай»)
   или `living_area` («Пришахтинск»)? Пока: если в строке нет улицы — `city`, если есть — `living_area`.
5. **RU/KZ интерфейс** — сейчас подписи на русском, парсер двуязычный.

### 9.1 Официальные файлы организаторов (`train.json`, `sample_input.json`, `sample_output.json`)

Официальный пример из ТЗ (`sample_input.json` → `sample_output.json`, запись `rec_00417`)
разбирается **полностью совпадающе по всем 13 полям**, включая восстановленный по справочнику
район `Ауэзовский`, которого нет в самой строке.

**Важно: по правилам кейса выданные данные нельзя выносить за пределы хакатона, поэтому их
нельзя коммитить в публичный репозиторий.** Кладите их в `data/official/` — эта папка уже
в `.gitignore`.

Как только файлы придут (одна команда):

```bash
mkdir -p data/official && cp train.json sample_input.json sample_output.json data/official/
python scripts/analyze.py data/official/train.json --out data/reports \
       --manual-hints data/manual/street_misses.json      # покрытие + дырки в справочнике
python scripts/analyze.py data/official/sample_input.json \
       --expected data/official/sample_output.json        # метрика + разбор ошибок
```

`scripts/analyze.py` показывает: заполненность полей, распределение confidence, строки, которые не
разобрались, «остатки» (что не отнесли ни к одному полю), улицы/города, которых нет в справочнике,
и сохраняет заготовку под ручное заполнение районов по проблемным улицам.

Что ожидаем от этих файлов и что с ними делать:

| Файл | Что даёт | Наше действие |
|---|---|---|
| `train.json` | несколько тысяч реальных строк **без разметки** | прогнать `analyze.py` → увидеть реальные форматы, дырки в справочнике, добавить проблемные улицы в `data/manual/`, поправить правила |
| `sample_input.json` | формат входа | сверить загрузчик (`/api/parse/batch/upload`) и ключи с нашим |
| `sample_output.json` | **единственная разметка** — эталон формата | сверить трактовки спорных полей (`district` в падеже строки, `living_area` vs `city` для посёлков, `street_type` при отсутствии в строке), прогнать `eval.py` |

Открытые вопросы к организаторам (задать в чате хакатона):
1. В `train.json` есть разметка или только строки? Совпадают ли `id` в `sample_input` и `sample_output`?
2. `district` сравнивается в написании из строки («Түрксіб») или каноническом («Турксибский»)?
3. Посёлок в составе города («Пришахтинск», «Боралдай») — это `city` или `living_area`?
4. `street_type` вне метрики: если в строке типа нет, ожидается `null` или подстановка из справочника?
5. Сколько записей в скрытом наборе и есть ли ограничение по времени на весь пакет?

### 9.2 Как проверялось качество

Разбор строится на явных правилах и справочнике — поэтому каждый шаг воспроизводим и проверяем:

* **Трактовки полей зафиксированы и обоснованы** (см. раздел 5): микрорайон как `street_name`
  против `living_area`, приоритет написания из строки над справочником, `city` против `living_area`
  для посёлков в составе города. Там, где ТЗ допускает вариант, решение описано словами, а не спрятано в коде.
* **Источники данных разобраны вручную:** две редакции КАТО (в свежей нет районов в городах),
  удалённая геометрия районов городов в OSM, выбор открытого GeoJSON-экстракта — всё это
  зафиксировано в разделе 4 вместе с датами и ссылками.
* **Сверка с официальным примером:** `rec_00417` из `sample_output.json`
  (`Мкр Аксай 3а` → `district = "Ауэзовский"`) совпадает поле в поле; эта запись закреплена тестом.
* **Приёмочное тестирование:** запуск в Docker, замер времени разбора, прогон без сети,
  проверка формата выгрузки.

**Проверяется запуском, а не «на словах»:** `scripts/selfcheck.py` (контрольные адреса),
`tests/test_parser.py` (19 тестов), `scripts/eval.py` (метрика по правилам ТЗ) — всё это
запускается одной командой `make check` и печатает результат. Комментарии в коде объясняют не
«что делает строка», а почему правило именно такое (например, в `app/textnorm.py` — почему слэш
между цифрами это дробь дома, а между словами — разделитель двух языков).

## 10. Как выложить в свой репозиторий

Обновление уже существующего репозитория одной командой:

```powershell
powershell -ExecutionPolicy Bypass -File deploy.ps1 -RepoPath D:\testhackatonrepo
```

Скрипт распакует свежий архив, скопирует файлы (не трогая `.git` и `data/official`), поднимет
контейнер с замером времени, прогонит самопроверку и сделает коммит с пушем.

```bash
cd jana-address                     # эта папка
git init
git add .
git commit -m "Jana Address: парсер адресов + справочник КАТО/OSM + API + интерфейс"
git remote add origin git@github.com:b1-o/Jana-Adress.git
git branch -M main
git push -u origin main
```

Перед пушем стоит убедиться, что `data/gazetteer.sqlite` (~14 МБ) и `data/osm/*.json` коммитятся —
без них образ не соберётся автономно. Если GitHub ругается на размер, включите Git LFS для
`data/gazetteer.sqlite` или оставьте в репозитории только скрипты сборки, а `.sqlite` собирайте `make build-all`.
